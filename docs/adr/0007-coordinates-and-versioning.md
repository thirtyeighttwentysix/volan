# ADR-0007: Coordinates, versioning and compatibility policy

- **Status:** accepted
- **Date:** 2026-07-26

## Context

Artifacts must be publishable to Maven Central, which requires a namespace the publisher can prove
ownership of. The project also needs a stated compatibility policy before it starts making promises in
a 1.0 release.

## Decision

- **Group id:** `io.github.thirtyeighttwentysix` — verifiable through the GitHub account that hosts
  the repository, so publication needs no domain purchase.
- **Artifact ids:** `volan-<module>` (`volan-runtime`, `volan-schema`, …), plus `volan-bom` for version
  alignment.
- **Root package:** `io.github.thirtyeighttwentysix.volan.<module>`.
- **Versioning:** Semantic Versioning. Before 1.0 the public API may change in minor releases; from
  1.0 the public ABI is checked in under `<module>/api/*.api` and any change to it must be an explicit,
  reviewed commit.
- **Java baseline:** JVM 17, compiled with `-release 17`, so a build on a newer JDK cannot accidentally
  reference newer APIs.
- **Generated code compatibility:** the generated client is bound to the runtime it was generated
  against by a generator version constant; the runtime refuses to load a client generated by an
  incompatible major version with an actionable error.

## Consequences

- Changing the group id later would be a breaking coordinate change, so it is fixed now, before any
  publication.
- The `api/*.api` dumps add review noise on every intentional API change. That is the point: the noise
  is the signal.

## Alternatives considered

- **`dev.volan`.** Shorter and prettier, but requires owning `volan.dev` and configuring DNS
  verification. Can be adopted later as an additional coordinate if the domain is acquired; the
  package name would move with it, so it is deliberately decided now rather than left open.
- **A single-segment group id.** Not accepted by Maven Central.
